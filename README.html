fetchconfig

A Perl tool for retrieving and archiving the running configuration of many network devices (Cisco, HP/Aruba, Juniper, FortiGate, and more) over telnet, SSH, SNMP+TFTP or HTTP.

We are looking for testers of this improved version.

This version should be config compatible to V0.25

01

Introduction

Need a browser-based UI? A companion project, fetchconfig-web, provides a web front-end on top of fetchconfig for browsing backups, viewing and comparing configurations, checking run status, and editing the device table: https://github.com/rainer-tammer/fetchconfig-web

Developers: DEVELOPER-GUIDE.md / .html is the architecture and engineering guide (internals, data structures, device-table format, security model, and how to extend); How-To-add-a-model.md / .html is the programming manual for writing a new device model; "perl Makefile.PL && make test" (or "prove -I. t/") runs the test suite under t/, and "make doc" regenerates the .md-derived docs via tools/render-doc.py and tools/md2html.py. Perl module requirements (core vs CPAN for Perl 5.26/5.28/5.40, by feature) are in the file DEPENDENCIES.

fetchconfig is a Perl script for retrieving the configuration of multiple devices. It has been tested under Linux, AIX and Windows, and currently supports a variety of devices, including Cisco IOS, Cisco Catalyst, Cisco ASA, Cisco PIX, FortiGate Firewalls, ProCurve, Alcatel Ethernet Routers (aka Riverstone), Dell PowerConnect Switches, Terayon 3200/3500 CMTS, Datacom DmSwitch Switches, HP MSR Routers, Mikrotik Routers, Tellabs MSR Routers, Juniper EX Switch JunOS, Oracle Acme Packet, Audiocodes Mediant, Cisco IOS XR, NEC Univerge IX, Hirschmann Railswitch, Zyxel switches, PLANET managed switches, Aruba CX switches, Cisco Nexus switches, AudioCodes Mediant SBCs, TP-Link Easy Smart switches, HP ProCurve 1700 series switches, and HP ProCurve ProVision (incl. 4000M/8000M) over SNMP+TFTP.

Important Change in 9.55 (filename_append_suffix)

Starting with 9.55, the filename_append_suffix option must start with a "." (e.g. ".txt"). A device whose suffix lacks the leading dot, or contains "/" or whitespace, now FAILS its backup with an error and writes nothing. If your device table carries a dotless suffix from an older version, fix it before the first 9.55 run. Also: do not add, remove or change a suffix on a device that already has backups; use "fetchconfig.pl -S" to find devices whose existing backups already mix suffixes. See filename_append_suffix under OPTIONS.

Important Change in 9.53 (Affects Every Device)

Starting with 9.53, saved configuration files end with a trailing newline on the last line, matching the device's own output (previously the last line had no terminating newline). This makes the files proper POSIX text files and matches what you get when downloading a config directly from a device's web UI.

This change touches EVERY model, not just one. Because the file content changes by that one final byte, the FIRST backup run after upgrading to 9.53 will report every device as "changed" (and, with changes_only, will save a new copy). This is a one-time effect of the newline fix, not real configuration drift; the second run onward compares clean again.

Installation (UNIX/Linux)

  1. fetchconfig.pl expects a Perl interpreter at /usr/bin/perl.
  1. Perl module requirements. See PERL MODULE REQUIREMENTS below for the full list and which ones each kind of device needs. In short: every run needs Net::Telnet and Net::SMTP; SSH devices additionally need Net::OpenSSH; the web-UI models need LWP::UserAgent and HTTP::Request::Common; and the procurve-snmp model needs Net::SNMP and Net::TFTP. All the other modules fetchconfig uses are part of the Perl core (5.26 and later; tested on 5.26, 5.28 and 5.40). Install whichever non-core ones you need (the file DEPENDENCIES lists every module, core vs CPAN for Perl 5.26/5.28/5.40, broken down by feature), e.g.:
	cpan install Net::Telnet Net::OpenSSH
  1. Unpack the fetchconfig tarball at a suitable location. Example:

[ fetchconfig tarball available at /tmp/fetchconfig-0.0.tar.gz ]

cd /usr/local
tar xzf /tmp/fetchconfig-0.0.tar.gz
ln -s fetchconfig-0.0 fetchconfig

[ fetchconfig is now available under /usr/local/fetchconfig ]

Perl Module Requirements

fetchconfig runs on Perl 5.26 or later. Most of the modules it uses are part of the Perl core on those versions and need no separate installation: Text::ParseWords, POSIX, IO::Handle, Time::HiRes, MIME::Base64, FindBin, File::Temp, File::Path, File::Basename, File::Compare, Getopt::Long, Digest::SHA and Net::SMTP.

The following modules are NOT in the Perl core and must be installed separately, but only if you use the devices that need them:

Net::SMTPNeeded on every run. It is part of the "libnet" distribution and ships with most Perl installations, but it is not in the Perl core. Note that fetchconfig loads its mail/reporting code on every run - it writes the per-device status file (see STATUS FILE) even when no e-mail is configured - so Net::SMTP must be present regardless of whether summary e-mail is enabled. 	cpan install Net::Telnet Net::OpenSSH

Usage

  1. Edit the file "device_table.example" according to your needs, and save it as "device_table". Example:

[ fetchconfig available under /usr/local/fetchconfig ]

cd /usr/local/fetchconfig
cp device_table.example device_table
vi device_table
  1. Run fetchconfig.pl, as in the following example:

[ fetchconfig available under /usr/local/fetchconfig ]

cd /usr/local/fetchconfig
./fetchconfig.pl -devices=device_table

The fetchconfig.pl script will scan the "device_table" file, trying to retrieve the configuration for every device, storing configuration files under the "repository".

By default the devices are fetched one after another, in device-table order. With many devices the run time is dominated by the network sessions; "-P N" fetches N devices concurrently - see PARALLEL FETCHING below.

06

Device Table

The device table assigned with the -devices= switch is a text file that supports two types of lines:

  1. Default-options lines assign default options to a device model. The following example adds some default options to the "cisco-ios" model:
#default	model		model-default-options
#
default:        cisco-ios       user=backup,pass=fran,enable=jose
  1. Device lines define the attributes of every device and optionally assign device-specific options. The following example defines a device named "vpn-gw":
#model		dev-unique-id	device-host	[device-options]
#
cisco-ios       vpn-gw          192.168.0.1     keep=10,changes_only=1

The dev-unique-id must be: a) an unique identifier across all devices; b) a valid filesystem's directory name.

07

Directory Allowlist

Optionally, the device table may restrict which directories a repository= or template_dir= option is allowed to name. This is useful when the device table is edited through a less-trusted front end (e.g. a web UI): the allowlist lives only in the real config file and cannot be widened from the UI, so an edit can never point a device at an arbitrary path.

The allowlist is written with "directory:" lines:

directory: repository $REPO1 /usr/local/fetchconfig/config directory: template $TEMPLATE1 /usr/local/fetchconfig/templates directory: fetch_run $CMD1 /var/fetchconfig/fetch_run directory: report $REP1 /var/www/fetchconfig/reports

Each line is: "directory:" <type> <$TAG> <path>, where <type> is "repository", "template", "fetch_run" or "report", <$TAG> is a unique $NAME symbol, and <path> is the allowed directory.

If a "directory:" section is present it must cover ALL THREE types (repository, template and fetch_run). The fetch_run type constrains on_fetch_run= (an external command): the directory of the command's program must be an allowed fetch_run directory. If on_fetch_run is not wanted at all, write "directory: fetch_run none", which satisfies the type and forbids any on_fetch_run. Similarly "directory: report none" satisfies the report type and disables change-report writing entirely.

Enforcement is OPT-IN: if the device table contains no "directory:" line, nothing is restricted (existing device tables are unaffected). If at least one "directory:" line is present, then every repository= and template_dir= used by a device (or inherited from a "default:" line) must be allowed:

  • repository= must name a "repository" entry; template_dir= a "template" entry; and on_fetch_run= must run a program whose directory is a "fetch_run" entry (the types are not interchangeable). - The value may be either the $TAG or the literal path (for on_fetch_run, "$CMD1/prog args" or "/dir/prog args"). A $TAG is expanded to its path internally. - Matching is exact, ignoring a single trailing slash. Paths are NOT canonicalized, so a symlinked, version-free path such as /usr/local/fetchconfig (a symlink to /usr/local/fetchconfig- 9.64) is compared as written and the version stays hidden. - Every path - in a "directory:" line and in a device value - is checked for illegal content: no "/../" or "/./" components, an absolute path, and only characters valid for the host OS; a bad path is rejected. - System directories are never accepted, allowlist or not (since 9.68): /bin, /sbin, /lib, /lib64, /usr/bin, /usr/sbin, /usr/lib, /usr/lib64, /usr/share, /usr/include, /etc, /boot, /dev, /proc, /sys, /run, /var/run, /var/lock, the root "/", and anything under them. A repository=, template_dir= or on_fetch_run program there is rejected and the device skipped.

A value that is off the list, of the wrong type, an undefined tag, or has illegal content is rejected at fetch time with a clear error, and that device is skipped; a bad value inherited from a "default:" line rejects every device that inherits it. The "--list-allowed-dirs" option prints the parsed allowlist (see the command-line options reference).

Without a "directory:" section nothing restricts where repository=, template_dir= or on_fetch_run may point, except the system-directory rule above, which always applies: a system directory is rejected whether or not an allowlist is present. Since 9.68 each distinct non-system directory in use is then reported once per run as "warning: ... has no directory: allowlist entry (unrestricted ...)", so you can see which paths are unrestricted and decide whether to add a "directory:" section. (A system directory never reaches this warning - it is rejected first.) The allowlist stays optional; an installation without one keeps working.

Email Notifications

fetchconfig.pl can e-mail a summary of a run's backup results as an HTML table (Device-ID, Date, Time, State, Size, Changes). This is entirely optional: unless an "email:" line is present, no SMTP connection is ever attempted.

The e-mail is laid out as a white rounded "card" on a grey canvas, with a dark-blue header bar carrying a small logo and "fetchconfig vX.Y", and the copyright footer below the card - matching the look of the fetchconfig-web mails. The header logo is embedded in the message itself (a multipart/related inline image); it is separate from the report_logo= used inside the on-disk HTML report.

The message is multipart: the HTML part above, and a plain-text part carrying the same statistics and per-device tables rendered as plain text (auto-sized columns, no diffs), so a text-only mail client or a notification preview still shows the result summary.

  1. Add an "email:" line to the DEFAULT OPTIONS SECTION (it is independent of any device model):
#email:	options
#
email:	from=config.backup@acme.com,to=admin@acme.com,smtp=mail.acme.com
OptionDescription
fromMandatory. The envelope/header sender address.
toMandatory. The recipient who receives the status of every device backed up in the run. Multiple addresses can be given separated by ';' (a comma cannot be used, since commas already separate options).
smtpMandatory. The SMTP server, as "host" or "host:port" (default port 25). Plain SMTP only -- no encryption.
userOptional. SMTP AUTH LOGIN username.
passwordOptional. SMTP AUTH LOGIN password. Only used (and AUTH attempted) when "user" is also given.
footerOptional. The copyright/attribution text shown in the summary e-mail's footer. The " - Version <n>" that follows it is fixed and always appended. If the value contains a comma, wrap it in double quotes (the quotes are stripped); an unquoted, comma-free value needs none. Default: "(c) 2006-2026 Everton da Silva Marques, Rainer Tammer and others".
portOptional. TCP port of the SMTP server. Works with every tls setting. Precedence: an explicit "port=" wins over a port given as part of the host ("smtp=mail.acme.com:587"), which wins over the default. The default follows the TLS mode: 25 for tls=off and tls=starttls, 465 for tls=ssl - so "tls=ssl" works without also setting the port. Must be 1-65535.
tlsOptional. Transport security for the SMTP connection: "off" (default - plain SMTP, the historical behaviour), "starttls" (connect in clear, then upgrade with STARTTLS; typically port 25 or 587) or "ssl" (TLS from the start; typically port 465). Both TLS modes need the IO::Socket::SSL module (which needs Net::SSLeay); plain SMTP needs neither. If TLS is requested but the module is missing, or the TLS handshake fails, the mail is NOT sent - fetchconfig never falls back to plaintext, as that would silently defeat the point of enabling TLS. Note that AUTH LOGIN sends the password base64-encoded (not encrypted); use "tls" whenever the SMTP server is not on a trusted network.

The "email:" line may be repeated; later values overwrite earlier ones for the same key (same rule as "default:").

  1. Optionally, override the recipient for one device with the device-specific "to=" option (available for all models):
#model		dev-unique-id	hostname	device-options
#
parks		lab209r		10.30.0.6	to=lab-owner@acme.com

A device whose recipient was overridden this way is left out of no one's mail: it is bundled with every other device sharing that same override recipient into one separate e-mail, sent only to that recipient, containing just their own device(s). The globally configured recipient (email: to=...) still receives the status of every device processed in the run, including overridden ones.

  1. The "Changes" column only reflects a changed-vs-previous comparison for devices where the run already performs one (changes_only=1, or on_fetch_run/on_fetch_cat set); for other devices it is reported as "n/a" -- no extra repository scan is performed just for this report.

Change Reports

fetchconfig can produce a change report after a run: an HTML page summarising which devices changed, with a coloured diff per changed device, plus up to a configurable number of diffs embedded in the summary e-mail. The report is written to an allowlisted "report" directory (see DIRECTORY ALLOWLIST) that fetchconfig-web presents (view/download/delete); it is NOT meant to be served to users directly. Options are set on "email:" lines:

email: report_dir=$REP1 the report directory (a "report" allowlist entry, by $TAG or path). email: write_report=on|off write the HTML report. With on and no from=/to=/smtp=, only the report is written and no e-mail is sent. email: email_max_diff=N embed up to N changed devices' diffs in the e-mail (device-table order). Default 0 (no diffs); 0 or unset = no diffs in the e-mail. email: web_report_url=URL base URL of fetchconfig-web (the CGI itself, with NO query string, e.g. https://host/cgi-bin/fetchconfig-web.cgi). fetchconfig appends "?action=view_report&file=<report>" automatically to build the "full report" link in the e-mail (only emitted when a report was actually written). Any query string already on the value is ignored. email: report_logo=FILE|none a logo file IN report_dir, embedded in the HTML (self-contained). Recommended size 250x50 px. none = no logo. email: report_days=N prune reports older than N days (only if N > 1; 0 or unset = no pruning). Deletes by exact filename, never a wildcard. email: mask_secrets=on|off mask common secret forms in the diffs (default on). Master switch for all hiding; applies to the e-mail and the HTML report. email: report_hide=<regex> additional custom regex, taken verbatim (whole rest of the line; one per line, accumulates); the matched substring is replaced with ****. Governed by mask_secrets. See CHANGE REPORTS below.

Device states in the report: initial (first backup, no diff), Changed (diff shown), Unchanged, Failed, and diff-unavailable (a changed device whose previous backup could not be read).

SECRET MASKING IS BEST EFFORT. When mask_secrets is on (the default), common Cisco/ProCurve forms are masked AFTER diffing, on both the old and new line, so a rotated secret still shows as a changed line (*** -> ***) without revealing either value. The built-in forms include SNMP community, type-5/7 secrets, enable secret hashes, key-string, pre-shared-key, wpa-psk, wpa-passphrase, a bare "key <hex>" and the Hirschmann "passwd <user> :vN:<hash>:" form (the username is kept, the hash masked). It is NOT comprehensive and is vendor- incomplete -- reports and report e-mails must be treated as sensitive regardless.

CUSTOM PATTERNS. For secrets the built-ins do not cover, add one or more regexes, one per line:

email: report_hide=(?<=wpa-passphrase )\S+ email: report_hide=(?<=^key )[0-9a-f]{16,}

Only the substring each regex MATCHES is replaced with "****", so to keep the surrounding keyword visible, match only the value -- the examples above use a fixed-width lookbehind "(?<=KEYWORD )" so the keyword stays and only the value is hidden, e.g.

wpa-passphrase c1ca253b... -> wpa-passphrase ****

Take care not to over-match: a pattern like "(?<=secret )\S+" would also fire inside words such as "my-secret". Patterns accumulate (one per line); comment a line out to stop hiding its pattern. They are governed by the mask_secrets master switch -- with mask_secrets=off nothing is hidden, built-in or custom. An invalid regex is logged and skipped (it never aborts the run).

VALUE SYNTAX. report_hide is special: everything after the first "=" on the line is taken VERBATIM as the regex -- the whole rest of the line, exactly as written. There is no comma splitting, no quote stripping and no space trimming for this option, so a regex may contain commas (e.g. the quantifiers "{m,n}", "{m,}"), "=", spaces and any other character with no escaping. Do NOT wrap the regex in quotes -- quotes would become part of the pattern. Put exactly one regex on the line; use additional report_hide= lines for more.

ARMORED DIFFS. Each device's diff in the HTML report is wrapped in a <div class="device-diff" data-device="<dev_id>" id="dev-<dev_id>"> with a stable structure, so an external program (fetchconfig-web) can reliably parse it and present an expandable per-device view. Treat this markup as a parse contract.

WARNING: the saved configuration files in the repository still contain cleartext credentials regardless of report masking; the report only masks what it displays, not what is stored.

REPORT DIRECTORY SETUP. So that fetchconfig-web (running as the web server's user/group) can read and manage the reports fetchconfig writes, set the group of report_dir to the web server's group and set the setgid bit on it:

chgrp <webgroup> /var/www/fetchconfig/reports chmod g+s /var/www/fetchconfig/reports

With setgid (g+s) set, every report file created in the directory automatically inherits the directory's group - fetchconfig needs no special privileges and does not change ownership itself. Ensure the directory's group permissions allow the web server to read (and, for the delete buttons, write) the files.

Retrieving a Stored Config, and Command-Line Options

In addition to fetching configuration from devices, fetchconfig.pl can also retrieve a configuration file already saved in the repository, without contacting the device again. This is done with the "-g" switch.

This is useful for scripting: e.g. dumping the latest config of a device to stdout, comparing today's config against yesterday's, or pulling out an older backup by its position in the history.

The examples below walk through retrieval and the related repository-maintenance modes; the full command-line option reference, grouped by purpose, follows at the end of this section under "COMMAND-LINE OPTIONS (reference)".

  1. Retrieve the latest (most recent) backup for a device, printing it to stdout:

[ fetchconfig available under /usr/local/fetchconfig ]

cd /usr/local/fetchconfig
./fetchconfig.pl -devices=device_table -g fw01.acme.net
  1. Retrieve an older backup, by passing "-n" together with "-g":
./fetchconfig.pl -devices=device_table -g fw01.acme.net -n 2
  1. List every backup on file for a device, to find out which "-n"/"-m" number to use:
./fetchconfig.pl -devices=device_table -l fw01.acme.net

Sample output (tab-separated: number, size in bytes, path):

1	28221	/usr/local/fetchconfig/config/202608/20260824/fw01.acme.net/fw01.acme.net.run.20260824.001105CEST
2	28221	/usr/local/fetchconfig/config/202608/20260823/fw01.acme.net/fw01.acme.net.run.20260823.001105CEST

The numbers in the first column are exactly the numbers "-n" and "-m" expect (1=latest, 2=next most recent, ...).

  1. Check whether any of a device's backups are 0 bytes long (e.g. a fetch that connected but failed to save anything):
./fetchconfig.pl -devices=device_table -z fw01.acme.net
If any are found, they are listed in the same format as
        "-l" above, and fetchconfig.pl exits with status 1; if
        none are found, nothing is printed and the exit status is 0.
  1. Run the same 0-byte check across every device in one go, instead of one device at a time, by using "-Z" (no dev_id) instead of "-z dev_id":
./fetchconfig.pl -devices=device_table -Z
Sample output if e.g. one device has an empty backup
        (tab-separated: dev_id, number, size in bytes, path):
fw01.acme.net	1	0	/usr/local/fetchconfig/config/202608/20260825/fw01.acme.net/fw01.acme.net.run.20260825.001105CEST
As with "-z", nothing is printed and the exit status is 0
        if no device has a 0-byte backup. A device whose repository
        can't be read is logged (to stderr) and skipped, without
        aborting the check for the remaining devices; that alone
        does not make "-Z" exit non-zero -- only an actual 0-byte
        backup does.
  1. Delete the 0-byte backups that "-z"/"-Z" find, by adding "-D". This removes only the empty backup FILES (never directories), and only for devices still in the device table -- "-z"/"-Z" look only at loaded devices, so a decommissioned device's leftovers are untouched here (those are orphaned files; clean them with "-o", below). Since this is destructive, preview it first by also adding "-T" -- with "-T" the delete commands are only logged (to stderr) as "would delete: unlink <path>", nothing is removed:
./fetchconfig.pl -devices=device_table -z fw01.acme.net -D -T
./fetchconfig.pl -devices=device_table -Z -D -T

Once the preview looks right, drop "-T" to delete for real:

./fetchconfig.pl -devices=device_table -z fw01.acme.net -D
./fetchconfig.pl -devices=device_table -Z -D
An emptied day/month directory is left in place; prune it
        afterwards with "-e -D" (see below). The exit status is
        unchanged by "-D": still 1 if any 0-byte backup was
        found, 0 otherwise. "-D" requires one of "-o", "-e",
        "-z" or "-Z"; "-T" requires "-D".
  1. Find backed up configs on disk that no longer have a matching device in the device table (e.g. a device that was decommissioned or renamed, leaving its old backups behind), with "-o":
./fetchconfig.pl -devices=device_table -o
Sample output if e.g. one old device's backups are found
        (tab-separated: dev_id, file count, total size in bytes,
        path to one date's worth of that device's backups):
old-switch01	1	28221	/usr/local/fetchconfig/config/202607/20260715/old-switch01
As with "-z"/"-Z", nothing is printed and the exit status is
        0 if nothing orphaned is found. "-o" scans every
        "repository=" path configured by a device in the currently
        loaded device table(s) (deduplicated -- most setups share
        one or a few repository paths); a repository path used only
        by a device no longer in the table won't be found this way,
        since there's nothing left to read that path from.
Besides the dated backup directories, "-o" also lists a
        removed device's <dev_id>.status and <dev_id>.debug files,
        which live at the repository root (not inside the dated
        directory). They are reported as single-file entries, and
        with "-D" they are deleted along with the orphaned backups.
        This matters for the .debug file in particular: it can hold
        credentials (see SECURITY NOTES), so orphan cleanup removes
        a decommissioned device's debug log rather than leaving it
        behind.
To actually delete what "-o" found, add "-D". Since this is
        destructive, preview it first by also adding "-T" -- with
        "-T", the delete commands are only logged (to stderr), not
        run:
./fetchconfig.pl -devices=device_table -o -D -T

Once the preview looks right, drop "-T" to delete for real:

./fetchconfig.pl -devices=device_table -o -D
The tab-separated listing on stdout (or "-f file") is the
        same either way, so a script parsing it doesn't need to
        care whether "-D"/"-T" were used; what "-D" does (or, with
        "-T", would do) to each orphaned directory is logged
        separately. "-D" requires "-o"; "-T" requires "-D" (both
        report an error and exit otherwise). With "-D" but not
        "-T", the exit status changes meaning: 1 if any deletion
        failed, 0 if nothing needed deleting or everything found
        was deleted successfully (with "-T", or with plain "-o",
        the exit status still just reflects whether anything
        orphaned was found).
6b. Check whether a device's backups have inconsistent
        filename suffixes (e.g. after filename_append_suffix was
        introduced on a device that already had backups), by using
        "-s dev_id", or "-S" to check every loaded device at once:
./fetchconfig.pl -devices=device_table -s fw01.acme.net
./fetchconfig.pl -devices=device_table -S
Nothing is printed and the exit status is 0 if every device's
        backups share one suffix (or none). Otherwise each inconsistent
        device is listed, one line per distinct suffix, and the exit
        status is 1.
6c. Find (and, with "-D", remove) empty directories left behind
        in the repositories, e.g. after deleting old backups by hand:
./fetchconfig.pl -devices=device_table -e
./fetchconfig.pl -devices=device_table -e -D -T   (preview)
./fetchconfig.pl -devices=device_table -e -D      (delete)
  1. Save the retrieved config to a file instead of printing it to stdout, by adding "-f":
./fetchconfig.pl -devices=device_table -g fw01.acme.net -n 2 -f config.file
  1. Compare two backed up versions of the same device, by adding "-m" together with "-n". The following example compares the latest backup ("-n 1") against the backup before it ("-m 2"):
./fetchconfig.pl -devices=device_table -g fw01.acme.net -n 1 -m 2

The output looks exactly like the output of the standard "diff" command run as "diff older newer", i.e. lines starting with "<" come from the "-m" (older) backup, lines starting with ">" come from the "-n" (newer) backup. As with "diff", the config file lists are otherwise unmodified.

The device-unique-id passed to "-g" (or "-l") is looked up in the device table(s) given with "-devices=" and/or "-line=" (see "EMBEDDING DEVICE TABLE INTO COMMAND LINE" above), exactly as when fetching; at least one of "-devices=" or "-line=" is therefore still required. Only the device's options (model, repository, etc.) are resolved from the device table -- the device itself is NOT contacted.

The options below are grouped by purpose. The retrieval options read back a stored config (the examples above show them in use); the housekeeping options check or clean the repository; the template options work with the generic model; and the generic options apply anywhere.

-eSwitches fetchconfig.pl to empty-directory check mode: scans every "repository=" path configured by a loaded device for empty directories in the three-level layout <repository>/YYYYMM/YYYYMMDD/<dev_id>/ and lists them, one tab-separated row per directory: <level>\t<path> (level = device, day or month) A directory is empty when it holds no entries at all; the scan works bottom-up, so a day directory whose only content is an empty device directory, and a month directory whose only content is such a day, are listed too. Only names of the expected shape are candidates (YYYYMM, YYYYMMDD whose first six digits match the month, and a dev_id- shaped name starting with a letter or digit); anything else in the repository, and the repository root itself, is never touched. Such leftovers typically come from deleting old backups by hand (before 9.56 also from "-o -D", which now cleans up after itself). Exit status is 1 if any empty directory was found, 0 otherwise. Honours "-f". Mutually exclusive with "-g", "-l", "-z", "-Z", "-o", "-s" and "-S". With "-D", the empty directories are DELETED, bottom-up: device directories first, then the day directories that are empty by then, then the month directories that are empty by then. Each removal is ONE plain rmdir on the exact, fully-qualified path - no wildcards, no recursive delete; rmdir cannot remove a non-empty directory, so files can never be taken along. Every command is reported as "deleting: rmdir <path>"; the rows gain a third column, deleted or failed. Exit status is 1 if any rmdir failed, 0 otherwise. "-e -D -T" reports "would delete: rmdir <path>" for each directory and deletes nothing.
-DRequires "-o", "-e", "-z" or "-Z". With "-z"/"-Z": also DELETES the zero-byte backup FILES found (one plain unlink per exact path; emptied directories are left for "-e -D" to prune). With "-o": also DELETES every orphaned device directory "-o" finds, not just lists it. The tab-separated listing (stdout/"-f") is unchanged; what's deleted (or, with "-T", would be deleted) is logged separately (to stderr): each backup file is deleted individually by its exact name (never a wildcard, never "rm -rf"/"rmdir /s"), logged as "rm <file>", followed by "rmdir <path>" for the now-empty directory. No shell command is actually spawned - deletion uses Perl's own unlink()/rmdir() directly; the logged lines are for your benefit, not literally executed. rmdir() only succeeds on a directory that's genuinely empty, so anything left behind unexpectedly (a file this scan didn't account for) makes that directory's removal fail loudly instead of being swept away regardless. A repository root itself (as opposed to an orphaned device directory under it) is never deleted, even if something unexpected made it look like a match. fetchconfig.pl exits with status 1 if any deletion failed, 0 if nothing needed deleting or everything found was deleted successfully.
-TDry run. With "-o -D", "-e -D", "-z -D" or "-Z -D": logs the delete commands "-D" would run (see above) without actually deleting anything. Also valid with "--clean-lock-dir" (shows which lock files would be removed). Requires "-D" except with "--clean-lock-dir". Exit status with "-T" is the same as the plain check - "-o": 1 if anything orphaned was found; "-e": 1 if any empty directory was found; 0 otherwise - since "-T" doesn't attempt any deletion to succeed or fail. Use it before a bare "-o -D" or "-e -D" to see what would be removed first.
-s dev_idSwitches fetchconfig.pl to suffix-consistency check mode for dev_id: checks that all of the device's backup files carry the same filename suffix. Reports the device if its backups mix suffixes - including "some with a suffix and some without", which is what happens when filename_append_suffix was added or changed after backups already existed (see the OPTIONS section). Prints one tab-separated line per distinct suffix: <dev_id>\t<suffix or (none)>\t<count>\t<example file> Nothing is printed if the device is consistent. A second step then compares the (single) suffix the backups use against the filename_append_suffix configured for the device in the device table, and logs a warning if they differ - for instance backups written before a suffix was configured, or a suffix that was later changed. This step is skipped for a device whose backups are already inconsistent. The summary line and exit status report the outcome: 0 backup suffixes are consistent, configured suffix matches backup file suffixes 1 found N device(s) with inconsistent backup suffixes, not checked against the configured suffix 2 backup suffixes are consistent, configured suffix does not match the backup file suffixes so it can be scripted. Honours "-f". Mutually exclusive with "-g", "-l", "-z", "-Z", "-o" and "-S".
-SLike "-s", but takes no dev_id and checks every device loaded via "-devices="/"-line=". "-S" is a pure consistency check: it does NOT compare against the configured filename_append_suffix (that second step is "-s dev_id" only). Exit status is 1 if any device's backups mix suffixes, 0 otherwise. Mutually exclusive with "-g", "-l", "-z", "-Z", "-o" and "-s". Note that "-s" takes a dev_id; "-s -f file" is rejected with "requires a device id" (the "-f" would be taken for the device). Write "-s dev_id -f file" or "-S -f file". How "-s"/"-S" tell the timezone token from the suffix: a backup is named <dev_id>.run.YYYYMMDD.HHMMSS<tz><suffix>, and <tz> is whatever strftime produced on the backup host - it differs by platform and CHANGES WITH DAYLIGHT SAVING TIME (AIX: CET in winter, CEST in summer; older AIX: NFT/DFT). The check therefore parses the tz token out first (numeric "+0200"/"-0500" on Linux and modern Windows; a bare name "CEST" on AIX; "-CEST" on Solaris; a multi-word name such as "W. Europe Standard Time" on Windows) and only then looks at what follows. The check ONLY WORKS if the suffix is separated from the tz by a ".", "-" or "_": "." is the rule since 9.55; "-" and "_" are accepted as separators so that backups written before that rule are still recognized. A DST change is therefore NOT reported as a suffix change. One inherent ambiguity: "-" followed by uppercase letters is the Solaris tz form, so an old suffix like "-BAK" on a timezone=hide backup (no tz token) is read as a tz; "_BAK", "-bak", or any suffix following a real tz token are unambiguous.

./fetchconfig.pl -devices=device_table -g fw01.acme.net > latest.cfg
./fetchconfig.pl -devices=device_table -g fw01.acme.net -n 1 > today.cfg

./fetchconfig.pl -devices=device_table -g fw01.acme.net -n 1 -m 2

Template-Driven Model (Generic)

Besides the per-device Perl models listed above, fetchconfig has a "generic" model whose device interaction is described by a TEMPLATE file instead of Perl code. A template is a small state machine of expect/send steps with the transport, prompt, timeouts, interrupt screens and ignore-lines as data. For a clean-CLI device this is a short file rather than a ~200-line module, and a family of similar devices can share or clone one template.

A device selects it in the device table with the model "generic" and a template name, for example:

	generic  sw1  10.0.0.1  model=cisco-ios,transport=ssh,user=...

This loads templates/cisco-ios.tmpl. transport is ssh or telnet. Templates for Cisco IOS/IOS-XE (both transports) and HP ProCurve (menu/VT100) are provided as worked examples.

Two companion tools support the workflow: tools/record-session.pl captures a real telnet/SSH session as a byte-accurate log to build a template from, and tools/generate_template.pl scaffolds a template draft from such a capture.

For Windows users without Perl, contrib/windows/ contains Python ports of these two tools - record_session.py and generate_template.py - with the same command line and the same .hex/.txt formats. build.cmd packages them into standalone record_session.exe and generate_template.exe with PyInstaller (no Perl, PuTTY or OpenSSH needed); the .py files also run on POSIX (paramiko is required for SSH). See contrib/windows/README.windows.

The generic model and its tools are documented separately:

  • README.generic-model -- the generic model and template grammar, quick reference
  • README.template_engine -- the full engineering reference: architecture, grammar, execution semantics, writing and generating templates
  • README.record-session -- the record-session.pl capture tool

The template parser is production-ready; the execution engine has been verified on Cisco IOS-XE over telnet and SSH and on an HP ProCurve menu switch. Verify a template against the target device before relying on it.

A template can be structurally checked without a device:

./fetchconfig.pl --check-template templates/cisco-ios.tmpl

The argument must be the FULL PATH to the .tmpl file - a bare template name is not resolved, because the same name can exist in different template_dir directories.

This runs the grammar and the load-time validator (self-loops, goto targets, capture markers, reachability, transport entry) and prints "ok" or the errors; it exits 0 on ok, 1 on errors, 2 on a file problem, and needs no device table. This is a STRUCTURAL check only - a template that passes may still need adjusting against the real device (prompts, show command, capture markers).

To list the templates available to the loaded devices:

./fetchconfig.pl -devices=device_table -t

"-t" (or "--list-template") scans every template_dir= a loaded device configures, plus the default template directory, and prints the template names it finds, numbered, one per line. It exits 0 if any template is found, 1 if none.

Troubleshooting

Note: some older SSH implementations (e.g. older HP/Aruba ProCurve firmware) only offer legacy key exchange algorithms that modern OpenSSH clients disable by default. fetchconfig.pl itself already re-enables what it needs for its own SSH connections (see the "KexAlgorithms"/"HostKeyAlgorithms"/ "Ciphers" master_opts in ProCurveSSH.pm and ComwareSSH.pm), so this only matters if you want to connect to the same device manually with the system's own "ssh" command (e.g. while troubleshooting) - the same kind of algorithm may need to be re-enabled in the SSH client's own configuration:

---[/etc/ssh_config]------------------------------
Host *
    KexAlgorithms +diffie-hellman-group1-sha1
---[/etc/ssh_config]------------------------------

The following device-locking options are available for all models, per-device and via "default:":

OptionDescription

fetchconfig 9.x and later only accept a suffix that starts with a "." (a file extension, e.g. ".txt" or ".cfg"). A suffix without the leading dot, or containing "/" or whitespace, makes that device's backup fail with an error and nothing is written. Decide on the suffix before the first backup. Web UI Backups (TP-Link Easy Smart, ProCurve 1700)

Some switches have no CLI at all - TP-Link Easy Smart switches (TL-SG105E, TL-SG105PE and siblings) and the HP ProCurve 1700 series. The tplink-web-sg105e and procurve-web-1700 models retrieve the config the same way a browser does on the switch's config backup page: they log in over plain HTTP (the switches offer no HTTPS), download the config file, and log out again. These models share their HTTP plumbing (AbstractHTTP.pm); the login, download and logout requests are per device, taken from packet captures of real browser sessions.

TP-Link: both session mechanisms seen on real devices are handled - the TL-SG105E binds the login session to the client's IP address, the TL-SG105PE v2 uses a session cookie. Either way the switch only allows a limited number of concurrent logins; if it reports the login table as full, the backup of that device is reported as failed rather than forcing another user out.

ProCurve 1700: the switch has only a manager password (the user option is ignored) and binds the session to the client's IP address. The config file it hands out ("switch.cfg") contains the SNMP communities and, apparently, the manager password in clear - protect the repository accordingly.

The downloaded config is an opaque binary file, not text. It is stored uuencoded ("begin 644 <name>.cfg" ... "end") so that it fits the text-based repository, the changes_only comparison and the -g retrieval like any other backup. To turn a backup back into the file the switch's restore page expects:

	uudecode -o config.cfg <backup-file>
or
	fetchconfig.pl -devices=... -g <dev_id> | uudecode -o config.cfg

A line-by-line diff between two backups (-m) is possible but not meaningful for these models - it only shows that, not what, changed.

ProCurve SNMP Backups

The older HP ProCurve ProVision chassis (4000M, 8000M) can only be managed remotely through a VT100 menu, which is not usable for scripted backup. They will, however, export a text copy of their configuration over TFTP when told to over SNMP, and that is what procurve-snmp does. It is a transport unlike the other models: no shell and no web UI, but SNMP plus TFTP, and hence no user/pass - the credential is the SNMP read-write community.

The sequence is: an SNMP set arms the switch's TFTP export, the config is fetched from the switch by TFTP, and a second SNMP set disables the export again. That disable always runs, even when the transfer failed, so the switch is never left with its TFTP server open.

The default remote_file "browse" produces a human-readable report (the "System Information / Port Settings / ..." listing). That is fine for backup and change tracking - which is what fetchconfig does - but it is a display export, not a file that can be TFTP'd back to restore the switch. Later ProVision models also accept remote_file=running-config, which is a replayable config; set the option accordingly on those.

Note on firewalls: the switch pushes the file to the backup host over TFTP (UDP/69 inbound, then a data port). A host firewall on the backup machine can block this; it then shows up as a TFTP get failure or timeout, not a hang.

Parallel Fetching

Fetching is sequential unless asked otherwise: one device at a time, in device-table order, with every log line shown as it happens. That is the right default for a handful of devices and for troubleshooting, but with thousands of devices the run time is dominated by the network sessions (roughly 5-15 seconds each, and a full timeout for every unreachable device), and a sequential run no longer fits in a night.

	./fetchconfig.pl -devices=device_table -P 20

"-P N" fetches with N concurrent worker processes. The parent process loads the device table, then hands out one device at a time to whichever worker asks next, so a slow device never holds up the others. Every worker is a copy of the fully loaded parent, so the models run unchanged. With N=10-20 a run of several hours typically completes in well under one; the gain is bounded by what the devices and the network tolerate, not by the backup host.

Output is atomic per device. While a worker fetches, everything it writes to stdout and stderr is buffered; when the device is finished the parent copies that buffer to the real stdout/stderr in one uninterrupted block. The output of one device is therefore never mixed with the output of another - each device's block looks exactly as it does in a sequential run (the "-----[dev]" banner, its log lines, any on_fetch_cat output). Two consequences of buffering: blocks appear in COMPLETION order, not device-table order; and a device's lines appear when it finishes, not live. At "-P 1" (the default) nothing is buffered and behaviour is unchanged from earlier versions.

Everything else is unaffected by concurrency: each device writes only its own directory, .status file and .debug file; the summary e-mail, the per-device to= bundling and the .status files are all produced by the parent from the workers' results, exactly as in a sequential run; keep=N expiry and changes_only comparison run per device as before. A worker that dies (perl error, killed, out of memory) is detected by the parent; the device it was fetching is recorded as failed (in the mail and its .status file) and the remaining devices are still fetched by the other workers.

Sizing N. Start at 10 and raise it while watching for devices that refuse or delay logins: the limits are the switches' concurrent-session caps, the TACACS+/RADIUS server's rate, and the links to remote sites - not the backup host. 10-25 is the typical range. "-P" applies to fetching only; it cannot be combined with the lookup/maintenance modes (-g, -l, -z, -Z, -o, -e, -s, -S), which stay single-process.

Security Notes

Debug files contain credentials. With debug=on, the per-device debug file <repository>/<dev_id>.debug records the session verbatim - for the telnet/SSH models that includes the login and enable passwords exactly as typed, and for procurve-snmp the SNMP read-write community. For the SSH models the file begins with the ssh client's debug trace (LogLevel=DEBUG, the same output as "ssh -v": key exchange, host key, authentication methods tried, "Authentication succeeded"); ssh never writes the password itself into that trace. Starting with 9.54 these files are created with mode 0600 (owner read/write only) regardless of the process umask. Still: only enable debug=on while troubleshooting, and delete the .debug file afterwards. Backup files, their directories and the .status file are created with the process umask - an unprivileged reader such as fetchconfig-web (running as "nobody" for -l/-g) must be able to read them, so they are deliberately NOT forced owner-only. (Parallel-fetch worker scratch files, which live in a private temp dir and are never read that way, are owner-only.) The backups do contain configuration secrets - and not always hashed: SNMP communities and some routing/VPN keys (BGP, OSPF, RADIUS/TACACS, IPsec pre-shared keys) are stored in cleartext, and Cisco "type 7" passwords are trivially reversible. Restrict the repository directory itself if the host is shared, and treat every backup as sensitive.

SSH host keys are not verified. The SSH models connect with StrictHostKeyChecking=no and UserKnownHostsFile=/dev/null, i.e. any host key is accepted and none is remembered. This is deliberate: fetchconfig runs as an unattended job, and a switch's host key changes on every hardware swap, which would otherwise stop the backup until someone edited known_hosts. The consequence is that an attacker on the network path could impersonate a device and capture the login password. Run fetchconfig on a trusted management network.

Device IDs are validated. A dev_id may contain letters, digits, underscore, dot and dash (so hostnames like sw01.example.com are fine) but may not consist only of dots, since "." or ".." would resolve to the repository itself or its parent.

SMTP. AUTH LOGIN sends the password base64-encoded, not encrypted; see the "tls" option under EMAIL NOTIFICATIONS. Header fields (From, To, Subject) have line breaks stripped before being sent, so a device-table value cannot inject extra mail headers.

Backup File Naming

Backups are named <dev_id>.run.YYYYMMDD.HHMMSS[<tz>][<suffix>], where <suffix> is the optional filename_append_suffix (must start with a "."; see the DEVICE OPTIONS section), i.e. with one-second resolution.

<tz> is whatever strftime produced on the backup host and so differs by platform and changes with daylight saving time: a numeric offset ("+0200", "-0500") on Linux and modern Windows; a bare name ("CEST" in summer, "CET" in winter; "NFT"/"DFT" on older AIX) on AIX; "-CEST" on Solaris; a multi-word name such as "W. Europe Standard Time" (or a localized one) on older Windows; or nothing with timezone=hide. Since 9.55 every operation that orders backups ("latest" for changes_only, keep=N expiry, -g/-n/ -m, -l, -z/-Z, -s/-S) orders them by the PARSED timestamp YYYYMMDD.HHMMSS rather than by a plain string sort of the whole name, so neither the tz token nor a suffix can disturb the order. Two backups of the same device completed within the same second would get the same name. Rather than let the second silently overwrite the first (and then compare the file with itself), the backup is written with O_EXCL: the second run fails to create the file and is reported, leaving the first intact. This essentially never happens for a real fetch (login, pager, full configuration, logout takes well over a second, and scheduled runs are minutes apart); and device locking (lock=on) prevents concurrent same-device runs outright. It only arises in artificial back-to-back test runs.

Status File

After every backup attempt, fetchconfig writes a small status file next to the backups, at:

	<repository>/<dev_id>.status

It is written for every device and every model, and does not depend on the "email:" line - it is a plain repository artifact, meant for external tools (for example a web front-end that reads backup_duration_sec to size a progress spinner). It is overwritten on every run and written atomically, so a reader never sees a half-written file.

The format is INI-style: a "[<dev_id>]" section header, then key=value lines:

	[swi-lab-01]
	backup_start_date=2026-09-11
	backup_start_time=22:14:03
	backup_end_date=2026-09-11
	backup_end_time=22:14:09
	backup_duration_sec=6
	backup_state=success
	backup_changed=changed

Fields:

FieldMeaning
backup_start_date / backup_start_timeWhen the fetch started (local time). Derived as end minus backup_duration_sec.
backup_end_date / backup_end_timeWhen the fetch finished (local time).
backup_duration_secWhole seconds the fetch took - the same value logged for the run and shown in the summary e-mail.
backup_statesuccess, failed, or skipped.
backup_changedunchanged or changed for a changes_only=1 device; forced for a changes_only=0 device (the backup is saved regardless of any comparison); unknown when the state is failed or skipped.
