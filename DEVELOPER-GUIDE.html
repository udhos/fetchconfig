fetchconfig — Developer Guide

This guide documents how fetchconfig works internally, the data structures it uses, the device-table format, the security mechanisms in place, and how to extend it. It is written for an engineer who needs to add functionality.

It complements, and does not replace, the following existing documents, which remain authoritative for their topics and are referenced from here:

  • README -- the user manual (installation, every option, email, the directory allowlist, command-line reference).
  • How-To-add-a-model -- the step-by-step recipe for a new device model.
  • README.generic-model -- the template-driven generic model & template engine: grammar and parser internals, execution semantics, writing and generating templates, and tools/record-session.pl for capturing a device session when writing a new model.
  • README.fc-snmp-inventory -- the read-only tools/fc-snmp-inventory.pl SNMP inventory probe: it drives SNMPInventory::collect so its output matches what the inventory feature stores, and shows which snmp-profiles.conf directive matched -- the tool for onboarding a device or vendor the inventory does not yet recognise.
  • DEPENDENCIES -- the Perl module dependency matrix.

Where this guide found those documents lacking a detail an extender needs, that detail is added here and noted as such.

Target version: 9.78. Perl floor: 5.26.

01

What fetchconfig is

fetchconfig is a command-line tool (not a daemon) that logs in to network devices, retrieves their running configuration, and stores a timestamped copy in a per-device directory, keeping only the configs that differ from the previous run. It is normally invoked from cron. A separate project, fetchconfig-web, is a CGI front-end that reads the stored backups and can invoke fetchconfig to run a backup on demand.

Key properties that shape the whole design:

  • One shot per invocation. fetchconfig parses its device table, fetches, writes, mails, and exits. It holds no state between runs except what is on disk (the backups, .status files, lock files).
  • Models never terminate the run. A device that fails to fetch is recorded as failed and the run continues to the next device. Only configuration errors in the device table or the directory allowlist abort before fetching.
  • The device table is the trust boundary. Whoever can write the device table supplies every device credential and can cause code execution via on_fetch_run. See Security mechanisms (Security).

The two phases

fetchconfig runs in two clearly separated phases. Keeping them separate is a deliberate design rule -- understand it before adding per-device behaviour.

Phase 1 -- parse and register (no fetching). fetchconfig.pl loads every -devices= file and every -line= argument and calls Detector::parse() on each line. parse():

  1. recognises the line type (email:, directory:, default:, or a device line -- see The device table format),
  2. for a device line, resolves the model, merges default: options with the device's own options into a fresh $dev_opt_tab, validates (dev_id pattern, numeric keep), and records the device in %dev_info_table + @dev_order.

No device is contacted in phase 1. The lookup modes (-g, -l, ...) use exactly this registration and then operate on the stored backups without ever entering phase 2.

Phase 2 -- fetch. After phase 1, fetchconfig.pl either dispatches to a maintenance/lookup mode and exits, or calls run_fetch_phase(), which iterates @dev_order and calls Detector::fetch_device($dev_id) for each -- sequentially, or in forked workers under -P (Parallel fetch (-P N)).

The per-device pipeline (fetch_device)

For each device, fetch_device() performs, in order:

  1. Resolve options needed up front: changes_only, on_fetch_run, on_fetch_cat, and whether a previous backup must be located.
  2. Locate previous backup (only when changes_only, on_fetch_run or on_fetch_cat needs it): find_latest scans the repository for the most recent prior backup, by parsed timestamp; the result feeds the compare in step 8. A freshly added device has none -- that normal first-run state is logged at info, inside the device's block. This runs before the guards below, so the scan happens even for a device a later guard will skip.
  3. System-directory check (always): reject a repository=, template_dir= or on_fetch_run program that points into a system directory; skip the device if so (Security mechanisms).
  4. No-allowlist warning (if no directory: section): warn once per run per distinct unrestricted directory.
  5. Directory-allowlist enforcement (only if a directory: section exists): repository=/template_dir= must resolve to an allowed path; on_fetch_run's program directory must be allowed; a $TAG is expanded to its real path. Off-list -> skip the device.
  6. Lock (if lock=on): acquire a per-device flock; on contention, retry, then record skipped and return (Locking).
  7. Fetch: $mod->fetch(...) -> the model's do_fetch() logs in, runs the show-config command, and returns the written backup path (or undef on failure). On debug=on, the session is captured to <dev_id>.debug.
  8. SNMP inventory (only when enabled for the device -- a community/user, and snmp_inventory not off; see SNMPInventory.pm). First the snmp_inventory_interval gate: if set and the last successful inventory (read from this device's .status via _status_inventory, keyed on inventory_at) is younger than the interval, the SNMP read is skipped and the prior result is carried forward into this run's .status (the DB row is left as-is) -- so a slow-SNMP device need not be read every run. Otherwise, right after the fetch, fetchconfig::SNMPInventory->collect(...) opens its own Net::SNMP session and reads the ENTITY-MIB (on v2c/v3: GET-BULK-walk entPhysicalClass for all rows, then GET the descriptive columns only for the parts it keeps, so a big stack's ports/sensors are not fully pulled; snmp_max_repetitions tunes it; v1 falls back to a full per-column walk). The full result (headline + every component + change history) goes to the DB via Mailer::record_inventory() / record_inventory_component() and the outbox (op=inv_*); the state + headline are also carried into the .status file -- fetch_device stashes the inv_* fields and passes them to every record_result call, and write_status_file writes inventory=<state> plus inventory_<field> lines. This runs independently of the config outcome and times itself separately (the config-retrieval log line excludes it); on failure with snmp_fatal=on the device is flagged so the driver exits 11.
  9. Compare: compare the just-written config against the previous latest backup located in step 2 (config_equal, ignoring volatile lines) to decide changed / unchanged / initial. No file is removed at this point.
  10. Record: Mailer::record_result(...) logs the per-device outcome and writes the .status file (including the inventory* keys from step 8). Its elapsed is time - $fetch_ts_start at this point, so backup_duration_sec spans the config fetch plus the SNMP inventory, not just the fetch.
  11. on_fetch_run / on_fetch_cat: if set, run the external program (shell-free; Security mechanisms) and/or copy the config to stdout. Both run regardless of whether the config changed.
  12. Discard: only if changes_only is set and the config was unchanged, delete the just-written file (config_discard) so only real changes are kept.
  13. Expire: purge_ancient deletes the oldest backups beyond keep=N; each backup it rotates out emits a DB expire event (Backup-history DB writer (optional)).

The lock filehandle is held in a lexical for the whole of fetch_device, so it releases automatically when the sub returns, by any path.

Sequence diagram -- one device through fetch_device

Time runs downward. --> is a return. A model's do_fetch is the only box that talks to the device; everything else is core. The three early guards (system-dir, allowlist, lock) can each end the device early with a recorded outcome.

Under -P, the whole column from fetch_device down runs inside a forked worker; the record_result payloads travel back to the parent through the result sink (Parallel fetch (-P N)), not shared memory.

Parallel fetch (-P N)

run_fetch_phase($parallel) runs devices concurrently when -P N is given (N >= 1 worker processes). It relies on POSIX fork, so it is a no-op on native Windows -- fetchconfig.pl forces -P 1 (sequential) there. The model is fork-per-device-batch:

  • The parent creates a private File::Temp work directory (0700, auto-cleaned).
  • It forks up to N workers; each worker runs fetch_device for its assigned device and writes its stdout/stderr to <tmpdir>/<dev_id>.out/.err (created under umask(077)), and its record_result payload to a result sink the parent reads back.
  • %email_config, the device table, and the result list live in the parent; each worker is an independent process, so per-package globals are isolated by the fork -- a worker cannot see another worker's state.
  • The parent installs SIG{INT}/SIG{TERM} handlers that forward the signal to the workers, so a killed parent does not orphan them.

Implication for extenders: anything a worker produces that the parent needs (a new per-device result field, a summary counter) must travel through the result sink (the serialized record_result payload), not a package variable -- a package variable set in a worker is lost when the worker exits. Mailer::record_result already serialises every key you pass it, so new result fields propagate automatically if you add them as record_result arguments.

The SNMP inventory collector (SNMPInventory.pm)

A model-independent, read-only collector (new in 9.80) run from fetch_device() after the config fetch, independent of its outcome. It reads the ENTITY-MIB and the system group over SNMP, derives a device headline plus a component list, and hands the result back to be written to the DB (via the outbox op=inv_*) and to the .status file (via record_result). Nothing here opens a DB handle or writes to a device -- it only issues SNMP reads. It also builds the shared Net::SNMP session for the procurve-snmp model. The user-facing config syntax lives in the snmp-profiles.conf header and in README.fc-snmp-inventory; this section is the implementation.

  • Session (open_snmp_session). Builds the Net::SNMP session (v1/v2c/v3, auth/priv, port/timeout/retries) from the snmp_* options -- the one place both the collector and procurve-snmp use. It turns off OCTET STRING hex translation, so a string field with a non-ASCII byte (e.g. an AP name with an umlaut) is read as UTF-8 text rather than Net::SNMP's 0x… rendering.
  • ENTITY-MIB walk (_walk_entity / _fetch_cells). On v2c/v3 it GET-BULK-walks only entPhysicalClass (tuned by snmp_max_repetitions), then _fetch_cells GETs the descriptive columns for just the parts it keeps -- so a big stack's ports/sensors are never fully pulled. On v1, or after a bulk error, it falls back to a full per-column get_table walk.
  • Headline + fallbacks. From the kept parts it derives vendor/model/serial/os_version, member_count, hw_set and the component list. Best-effort fallbacks for sparse ENTITY-MIBs: os_version from sysDescr (_os_from_sysdescr), model from a sysObjectID lookup (_model_for), and member_count from the chassis count when no chassis carries a serial. The system group also yields sysname/syslocation/syscontact -- a device-level admin headline, read on every device and stored where the 2.17 columns exist (current-state only, never a change trigger).
  • Stack-entity promotion. When the table has no chassis(3) entry but one or more stack(11) entries (e.g. a Zyxel single-unit switch that reports one top-level stack), those are promoted to chassis so their model/serial/OS are harvested by the full derivation instead of dropping to the headline path. A device with a real chassis ignores its stack entry.
  • ENTITY-less headline. A device with a live system group but no entPhysicalTable at all (e.g. Hirschmann classic switches, Aruba WLAN APs) yields a one-device headline instead of a failure: vendor from the sysObjectID enterprise, model/serial/OS filled from the vendor profile (below), and a final sysDescr parse for the OS.

Profile directives (snmp-profiles.conf, matched most-specific-first by the shared _spec_for) -- the config syntax is documented elsewhere; the implementation:

  • vendor / model -- the enterprise→name registry (_vendor_for) and a sysObjectID→model last-resort map (_model_for).
  • oid (_override_oid / _apply_override_oids) -- fill an empty headline field from a vendor private-MIB OID on an ENTITY-less device (ENTITY data always wins).
  • override (_override_field / _override_value) -- replace a present-but-wrong (or missing) field from sysdescr/entdescr/entmodel/entserial or a numeric OID, with an optional capture regex, consulted before the ENTITY value.
  • A numeric oid/override OID ending in .* is a table-column base: _get_instance($session, $oid, $walk) does one GETNEXT and takes the first row in that column instead of a plain GET -- opt-in per rule (the .* marker is a third spec element), so other vendors' instance OIDs keep exact-GET.
  • members (_members_for / _collect_members, via the generic _walk_column) -- one chassis component per row of a vendor member table: it walks the serial= column (which enumerates the members) and joins model=/name=/os= by the per-row index, with primary = the row whose name matches sysName.

Both oid and override also run on the ENTITY-less path. Aruba WLAN is the worked example: enterprise 14823 "Aruba Networks" (built-in vendor) + override model 14823 sysdescr MODEL:\s*([^)]+) + a members 14823 …aiAPTable line for a virtual controller's member APs.

  • Firmware cleaning (_fw_clean). Per-component fw_version (entPhysicalFirmwareRev) is passed through _fw_clean, which drops placeholder values (empty, or the Cisco Catalyst 9000 chassis 0.1) so a bogus firmware is stored as NULL (on some platforms the real ROMMON is not in SNMP at all -- see the DB schema contract).
  • Structure / helpers. collect() opens the session, delegates the read-only derivation to _collect_session() -- the same step tools/fc-snmp-inventory.pl drives directly -- and closes. mode() is the per-device enable/disable gate; _load_profiles() / _profile_path() parse and locate snmp-profiles.conf (cached for the run); flag() is the permissive boolean for the snmp_* flags; and _clean_scalar / _trim / _opt / _norm_version are the small helpers.
03

Data structures

All of these are file-scoped (my) package variables unless noted. "File" = the .pm that declares them.

Detector.pm -- the device registry

  • %model_table : label -> model object. Populated by Detector::init, which constructs one instance of every model class and calls Detector->register($mod) for each (the models do not self-register). label is the device-table name (cisco-ios, generic, ...).
  • @dev_order : ordered list of dev_ids in device-table order. The sequential fetch phase iterates this; the maintenance modes use it to list devices deterministically.
  • %dev_id_table : dev_id -> source line number. Used to detect and report a duplicate dev_id.
  • %dev_info_table : dev_id -> a hashref describing the device:
perl 
{
  model       => $mod,          # the model object (from %model_table)
  dev_host    => $dev_host,     # hostname or IP (2nd field of the device line)
  dev_opt_tab => $dev_opt_tab,  # the merged per-device option hash (see 3.2)
  file        => $file,         # source device-table file (for messages)
  num         => $num,          # source line number
  line        => $line,         # the raw source line (for messages, masked)
}
  • The directory-allowlist structures (populated from directory: lines):
  • %dir_allow_tag : $TAG -> { type => repository|template|fetch_run|report|lock, path => <abs path> }. The $TAG indirection a device value uses.
  • %dir_allow_path : normalised allowed path -> type, for membership tests.
  • $dir_allow_present : true once any directory: line has been seen (switches the allowlist from "off/opt-in" to "enforced").
  • @dir_allow_rows : ordered [type, tag, path] for --list-allowed-dirs.
  • @dir_allow_errors : [reason, ...] for each rejected directory: line; a non-empty list aborts the run before any fetch (Security mechanisms) and is what --list-allowed-dirs lints.
  • $dir_allow_fetch_run_none / $dir_allow_report_none : set by directory: fetch_run none / directory: report none (disable that capability).
  • %warned_unlisted_dir : dedup set for the "no allowlist entry" warning, reset per device-table load.
  • @SYSTEM_DIRS : the list of directories (/bin, /etc, /usr/lib, ...) that are never acceptable as a repository/template/fetch_run directory, tested by _system_dir_path().
  • $DEV_ID_RE = qr/^[\w.-]+$/ : the allowed dev_id character set. A dev_id is also rejected if it is only dots.
  • $default_lock_dir : <canonical dir of fetchconfig.pl>/.lock, set by Detector::init($log, $lock_dir) from the driver.
  • $lock_dir_failed : set if any device's lock dir could not be created or used; the driver turns this into exit 10 after the run.

$dev_opt_tab -- the per-device option hash

The single most important structure for an extender. It is a flat hashref: option name -> string value, built in phase 1 by merging the model's default: options under the device line's own options (device wins). Every option in The device table format appears here by its bare name (repository, pass, keep, debug, lock, to, ...). Models and the pipeline read it only through the Abstract accessors, never by direct hash access:

  • dev_option($tab, $name) -- the effective value, with a $TAG expanded to its real path for directory-valued options, and with timeout-family options validated (a non-positive-integer timeout/fetch_timeout/banner_timeout/ prompt_settle_ms is ignored so the documented default applies).
  • dev_option_raw($tab, $name) -- the effective value with no $TAG expansion (used by the allowlist enforcement, which must see the raw value).
  • dev_option_flag($tab, $name, $default) -- a boolean option (on/off), e.g. debug, lock, changes_only (where applicable).
  • dev_option_posint($tab, $name, $default, $allow_zero) -- a validated non-negative/positive integer, e.g. lock_retry (0 allowed), lock_retry_time (>=1).

To add an option: decide whether it is directory-valued (add it to %DIR_VALUED_OPTION in Abstract so $TAG expands), numeric (read with dev_option_posint), boolean (dev_option_flag), or plain (dev_option). No parse change is needed -- parse_options accepts any key=value; the option "exists" as soon as something reads it.

Mailer.pm -- the result record

  • @results : one hashref per device outcome, pushed by record_result(%args). Under -P every field is serialised through the result sink; the .status file gets only a derived subset (backup_start/end_date, backup_start/end_time, backup_duration_sec, backup_state, backup_changed), not these fields verbatim. The fields:
perl 
{
  dev_id     => ...,   # device id
  dev_host   => ...,   # hostname/IP
  ts         => ...,   # epoch of the fetch start (for Date/Time columns)
  elapsed    => ...,   # seconds the fetch took
  success    => 0|1,   # hard success/failure (undef on a 'skipped' row)
  size       => ...,   # backup size in bytes, or undef
  changed    => 'changed'|'unchanged'|'initial'|'n/a',
  state      => 'skipped' (optional; explicit state wins over success)
  repository => ...,   # so the per-device .status file can be written
  to         => ...,   # device-specific recipient override (the `to=` option)
}

The effective State shown in the mail is computed by row_state($row): an explicit state (currently only 'skipped') wins; otherwise success ? 'success' : 'failed'.

  • %email_config : the parsed email: options (from, to, smtp, user, password, tls, report_dir, write_report, email_max_diff, web_report_url, report_logo, report_days, mask_secrets, footer).
  • $rep_url, $rep_email_diffs, $rep_max_diff, $rep_mask : material carried from send_summaries into the HTML/text builders (the report link, the diffs to embed, the diff cap, the masking flag).
  • $MAIL_LOGO_B64 : the inline e-mail header logo (base64 PNG), embedded as a multipart/related Content-ID: <fcwlogo> part. Independent of the on-disk report's report_logo=.

On-disk structures

  • Backup file : <repository>/YYYYMM/YYYYMMDD/<dev_id>/<dev_id>.run.YYYYMMDD.HHMMSS[tz] (optionally plus filename_append_suffix). parse_backup_filename() and sort_backups_desc() parse and order these by the parsed timestamp YYYYMMDD.HHMMSS, never by a plain string sort of the whole name (so the timezone token and a suffix cannot disturb the order). Written with O_EXCL so two runs completing in the same second cannot silently overwrite one another (Security mechanisms).
  • .status file : <repository>/<dev_id>.status -- the last-run result for that device (written atomically via a dotfile temp + rename -- the temp, not the final file, carries the leading dot), consumed by fetchconfig-web and the maintenance modes.
  • .debug file : <repository>/<dev_id>.debug -- the full session trace when debug=on (0600; Debug tracing (debug=on)). Overwritten each run.
  • Lock file : <lock_dir>/<sha256(dev_id)>.lock -- a flock holder, never unlinked on release (Locking).
04

The device table format

The device table is a line-oriented text file (one or more, via -devices=; individual lines can also be injected with -line=). Blank lines and # comment lines are ignored. There are four line types, recognised by prefix.

Device line

<model>  <dev_id>  <host>  <opt1=val1,opt2=val2,...>
  • <model> -- a registered model label (e.g. cisco-ios, generic).
  • <dev_id> -- the unique device id. Must match ^[\w.-]+$ and must not be only dots. It is the directory name under the repository and the key in every status/lock/result structure. A device id is never user-free-form: it is validated at load time.
  • <host> -- hostname or IP used to connect.
  • the option list -- comma-separated key=value pairs. A value may be double-quoted to contain a comma or spaces (e.g. pass="a,b c"). A value of the form $TAG is a directory-allowlist tag, expanded for directory-valued options.

Example:

cisco-ios  rtr01  10.0.0.1  user=backup,pass="s3cr3t",enable=en,repository=$REPO1,keep=30

default: line

default:  <model>  <opt1=val1,...>

Sets per-model default options. A device line of that model inherits these unless it overrides them. Merging is per-option (device value wins). A bad value inherited from a default: line (e.g. a non-numeric keep) rejects every device that inherits it.

email: line

email:  from=...,to=...,smtp=...,...

Configures the summary e-mail. If no email: line is present, no SMTP connection is ever attempted. Options: from, to, smtp (host or host:port), user, password, tls (off|starttls|ssl), report_dir, write_report (on), email_max_diff, web_report_url, report_logo

(FILE|none), report_days, mask_secrets (off to disable), footer. See README -> EMAIL NOTIFICATIONS for each.

directory: line (the allowlist)

directory:  <type>  <$TAG|none>  [<abs-path>]

<type> is repository, template, fetch_run, report, or lock. Presence of any directory: line turns the allowlist on; thereafter a device's repository=, template_dir=, and the on_fetch_run program directory must resolve to an allowed path (directly or via a $TAG). (lock is an accepted directory: type that lock_dir= can resolve a $TAG through, but lock_dir= itself is not allowlist-enforced -- it is only $TAG-expanded and system-directory-checked.) directory: fetch_run none / directory: report none disable that capability. A directory: line that names a system directory, or is otherwise malformed, is recorded in @dir_allow_errors and aborts the run before any fetch. See README -> DIRECTORY ALLOWLIST for the full semantics and --list-allowed-dirs for the linter.

pw: line (credential aliases)

pw:  user  $Alias  <username>
pw:  pass  $Alias  <secret>

A pw: line registers a named credential alias, the same way a directory: line registers a $TAG. parse_pw_line validates the kind (user or pass), the alias name (^\$[A-Za-z_][A-Za-z0-9_]*$ — $ then a letter or _, never a leading digit), rejects duplicates and any clash with a directory: $TAG, and dequotes the value through Abstract::dequote_value; pass values are masked in logs.

A credential-slot value is interpreted by the first character of its raw token (Abstract::_expand_pw_alias, reached via _resolve_alias): a leading " is a quoted, fully-verbatim literal (dequoted, never an alias); a leading $ matching the name grammar is an alias reference (resolved, kind-checked — user/snmp_user take user aliases; pass/enable/snmp_community/ snmp_write_community/snmp_authpass/snmp_privpass take pass aliases; an undefined or wrong-kind alias logs an error and yields undef); anything else is a verbatim literal with a first-character-only de-escape (_deescape_first: leading \$→$, leading \\→\, interior untouched). So the two ways to write a $-leading literal are \$value or "$value". To keep the quoted-ness available to the resolver, parse_options stores credential slots' raw token (quotes intact) — it skips dequote_value for the %PW_SLOT_KIND options and the resolver does the dequote.

Malformed pw: lines accumulate in @pw_errors (accessors pw_errors / pw_present / pw_alias / pw_rows); like directory: errors they abort the run (exit 2) before any fetch. --list-credentials lists the defined aliases (values masked) and lints them — malformed lines plus a cross-table check that every credential reference resolves to a defined alias of the right kind — exiting 2 on any problem, so fetchconfig-web's validate_table_with_fetchconfig can gate saves on it.

Options available for all models

debug, to, on_fetch_run, on_fetch_cat, timezone, filename_append_suffix, comment, site, and the locking options (lock, lock_dir, lock_retry, lock_retry_time) are available for every model. The SNMP inventory options (snmp_community/snmp_write_community/snmp_user, snmp_version, snmp_port, snmp_timeout, snmp_retries, snmp_max_repetitions, the v3 snmp_level/snmp_authproto/snmp_authpass/snmp_privproto/snmp_privpass, and snmp_inventory/snmp_inventory_level/snmp_inventory_history/snmp_fatal/snmp_inventory_interval) are also model-independent -- the collector reads them through dev_option on any model (see SNMPInventory.pm and the per-device pipeline). Exception: snmp_profile_file is read through default_option, so it is default:-only -- the only device-table option restricted to default: lines (a device-line value is ignored, with a warning), because the parsed vendor/model file is cached process-wide. procurve-snmp additionally consumes snmp_community/snmp_write_community/snmp_timeout/snmp_version as its own transport credentials via the shared open_snmp_session. Model-specific options (user, pass, enable, timeout, repository, keep, fetch_timeout, changes_only, ...) vary by model -- see the per-model options tables and the model sections in README (the DEVICE OPTIONS section). Note procurve-snmp no longer reads the shared timeout (9.80): its timeout is snmp_timeout.

05

Models and the model API

Lifecycle

Each model is a subclass of fetchconfig::model::Abstract. Detector::init constructs one instance of every model class and calls Detector->register($mod) for each, which puts it in %model_table under $mod->label. (Models do not self-register; adding a model means adding its register(...->new($log)) line to Detector::init.)

Per device, Detector::fetch_device calls $mod->fetch(...), whose default implementation in Abstract delegates to the model's do_fetch(...). A model therefore implements do_fetch (and label), and overrides prompt/login hooks as needed; everything else is inherited.

The shared API (Abstract.pm)

The methods a model (or an extender) relies on. Signatures are indicative; read Abstract.pm for exact argument lists.

Session / transport

  • ssh_open($dev_host, $dev_user, $dev_pass, $dev_timeout, $debug_fh) -- open a Net::OpenSSH session (SSH models). Host-key policy (accept any key, keep none) is set here.
  • open_ssh_debug_file(...) / open_telnet_debug_file($t, $dev_opt_tab, $repo, $dev_id, $dev_host) -- when debug=on, open <dev_id>.debug (0600) and attach it as the SSH/telnet session log. The telnet helper (9.71) is what gives every telnet model debug=; call it right after the connection opens and close() the returned handle at session end.
  • wait_for_command_prompt(...), expect_enable_prompt(...), expect_enable_prompt_paging_auto(...), drain_until_idle(...), chat_banner(...), chat_show_conf(...) -- prompt and login helpers. Models override prompt_head() / prompt_tail() / interrupt_screens() / ssh_extra_opts() to tune behaviour.

Backup write / compare / expire

  • dump_config($dev_id, $dev_opt_tab, \@lines) -- write the backup (O_EXCL, umask-driven perms, repository dir auto-created), returns ($dir, $file).
  • find_latest($dev_id, $dev_opt_tab) -- locate the most recent prior backup.
  • config_equal(...) / config_equal_ignoring_lines(...) -- compare two configs, ignoring volatile lines.
  • config_discard($dir, $file) -- remove the just-written backup when it equals the previous one, and prune the dir if emptied.
  • purge_ancient($dev_id, $dev_opt_tab) -- delete backups beyond keep=N (validates keep; Security mechanisms).

Options / secrets / text

  • dev_option* accessors ($dev_opt_tab -- the per-device option hash).
  • print_secret($t, $secret) -- send a password/secret to the device without logging it (suspends the debug log around the send, writes a masked marker). Every model sends credentials through this; a new model MUST too.
  • mask_secrets($line) -- redact pass=/enable=/community=/password=/ secret=/key=/token=-style values, plus the SNMP secrets snmp_community=/snmp_write_community=/snmp_authpass=/snmp_privpass= (9.80), before echoing a device-table line to the log.
  • stripansi($s), regexp_quote_keep_bytes($s), escape_brackets($s), dequote_value($s) -- text helpers (ANSI stripping, byte-preserving regex quoting for learned prompts, etc.).

Locking

  • lock_dir_resolve, device_lock_path, acquire_device_lock (Locking).

Call graph -- core <-> model <-> Abstract

How control flows into a model and what the model calls back. ( ) = a hook the model overrides; [ ] = a shared helper the model calls. Arrows point from caller to callee.

Rule of thumb: a model implements label + do_fetch and overrides only the prompt/transport hooks it needs; it calls the [ ] helpers for everything else and never reimplements them. These core-driven helpers -- config_equal, config_discard, purge_ancient, locking, and find_latest (which core calls before the fetch) -- run in core, not the model; a model just returns the written path.

Adding a model

Follow How-To-add-a-model (the authoritative recipe) together with the data-flow context in The per-device pipeline (fetch_device)/The shared API (Abstract.pm). In short: create fetchconfig/model/Yours.pm as an Abstract subclass, implement label and do_fetch, send credentials with print_secret, call open_telnet_debug_file/open_ssh_debug_file so debug= works, write the config with dump_config, and register the model. Add it to t/00-compile.t's expectations and the per-model matrix in the HTML docs. Capture a real session first with tools/record-session.pl (see README.generic-model).

For a device that speaks a config-template rather than a bespoke dialect, prefer the generic model and a template -- see README.generic-model; no Perl is needed.

Debug tracing (debug=on)

debug=on writes a 0600 <repository>/<dev_id>.debug session trace, available for every model (since 9.71). Three mechanisms, all producing the same file contract:

  • SSH models -> open_ssh_debug_file (records the ssh -v trace + session).
  • Telnet models -> open_telnet_debug_file (attaches the Net::Telnet dump_log).
  • HTTP / SNMP models -> their own implementation (HTTP request/response; SNMP operations + TFTP transfer).

Credentials never reach the log because models send them via print_secret, which suspends the log around the send. The file still contains configuration secrets (hashes, community strings), so it is 0600 and should be deleted after troubleshooting.

08

Locking

lock=on serialises concurrent backups of the same device (overlapping cron, or a web "Backup Now" over a cron run). Mechanism:

  • Key: sha256_hex(dev_id); path: <lock_dir>/<hash>.lock.
  • Lock dir: lock_dir= (a directory: lock $TAG or a path), else the default <dir of fetchconfig.pl>/.lock, created 0700. If it cannot be created/used, the run exits 10 at the end.
  • Acquire: sysopen(..., O_RDWR|O_CREAT|O_NOFOLLOW, 0600) then flock(LOCK_EX|LOCK_NB). On contention, retry lock_retry times (default 5; 0 = skip immediately) at lock_retry_time-second intervals (default 10), then record the device as skipped and continue. The process exit code is not changed by a lock-skip.
  • Release: automatic when the holding process exits (even on crash). The lock file is never unlinked on release (unlinking would open a two-holders race). --clean-lock-dir removes stale files flock-first.

Works across the forked -P workers and across separate invocations. Requires a local filesystem (flock over NFS on AIX is unreliable) -- a documented operator responsibility.

Device-table file lock (<devices>.lock)

Separate from the per-device lock above, and about the table file rather than a device. --rename-device-id rewrites a device-table line in place; a concurrent fetch run must not parse a table mid-rename. The lock object is a sidecar <devices>.lock next to each -devices= file (not the file itself: the rename swaps the table's inode via temp+rename, so a lock on the file's own descriptor would not cover the swap), handled by fetchconfig::Lock:

  • A normal run takes a shared lock (LOCK_SH) while load_device_list parses each -devices= file, with a 2 s bounded, non-blocking acquire, released before fetching. On timeout it logs and exits 2 rather than parse a table a rename is changing.
  • --rename-device-id / --replay-db-change take an exclusive lock (LOCK_EX), the rename holding it across the re-check, the on-disk sweep and the atomic table rewrite.
  • If the sidecar cannot be created (e.g. a read-only directory), a run proceeds without the lock (fail-open, so locking never breaks an existing deployment); a rename refuses (fail-closed, for safety).

Like the per-device lock this is flock-based, so the same local-filesystem requirement applies. NB: on AIX flock is emulated via per-process fcntl locks, so contention is only meaningful between processes (a run vs a rename), which is the only case that matters here.

09

Security mechanisms

Trust model (read this first)

  • The device table is the credential store and a code-execution surface. Whoever can write it already holds every device password and, via on_fetch_run, can run a program as the fetchconfig user. The security mechanisms below defend against content mistakes and external attackers, not against a hostile table author -- that is out of scope by construction.
  • fetchconfig-web split. In the fetchconfig-web deployment, content is read as the unprivileged nobody user (-l/-g) and backups are written as root via sudo (-g/-o). This is why repository files/directories are deliberately umask-readable, not owner-only (see 9.6) -- an unprivileged reader must be able to read them.

Credential handling

  • print_secret sends passwords to the device without logging them (suspends the session log around the send, leaves a masked marker). Every model uses it.
  • mask_secrets (Abstract, for device-table lines echoed to the log) redacts pass=/enable=/community=/password=/passphrase=/secret=/key=/token=-prefixed values and the SNMP secrets snmp_community=/snmp_write_community=/snmp_authpass=/snmp_privpass= (9.80), quoted values included, so a malformed table line in an error message does not leak a credential. (Detector has its own, narrower masker for the lines it logs: it covers pass=/enable=/community= and the four snmp_* secrets, but not quoted values -- not a copy of Abstract's.)
  • mask_line (Report, for config content in the HTML report and the mailed diffs) redacts secret N <hash> / password N <hash> forms. It is best-effort and biases toward masking (a false positive hides a non-secret in the diff view; never the reverse).

Command execution -- on_fetch_run

on_fetch_run is executed without a shell: the configured value is split into argv with Text::ParseWords::shellwords and run with the list form of system (system { $argv[0] } @argv), which goes to execvp() directly. Shell metacharacters (;, |, $(...), backticks, >) are passed to the program as literal text, not interpreted. The program must not live in a system directory. A start failure, signal, or non-zero exit is logged.

Path safety

  • dev_id whitelist ^[\w.-]+$ (dots-only rejected) -- prevents a device id from escaping the repository via ../.
  • Directory allowlist -- when a directory: section exists, repository=, template_dir=, and the on_fetch_run program directory must resolve under an allowed path; paths are checked for /../, /./, absolute form, and legal characters; a $TAG is expanded. Off-list -> device skipped. (lock_dir= is not allowlist-enforced -- it is only $TAG-expanded and system-directory-checked.)
  • System-directory rejection (_system_dir_path) -- repository=, template_dir=, the on_fetch_run program directory and lock_dir= may never be /bin, /etc, /usr/lib, ... or the root, with or without an allowlist. A directory: line that declares one is rejected at parse time.
  • Abort on a broken allowlist -- if any directory: line failed to parse, the run aborts (exit 2) before any fetch, rather than continuing with a silently reduced allowlist (fail-closed).
  • O_EXCL backup write -- dump_config creates the backup exclusively, so two runs finishing in the same one-second filename window cannot silently overwrite each other (the second is refused and reported).

Locking

See Locking -- O_NOFOLLOW on the lock file, 0600 lock files, 0700 lock dir, flock-based, never-unlink-on-release, flock-first cleanup.

File permissions

Backup files and their directories, and the .status file, are created with the process umask -- deliberately not forced owner-only, because the fetchconfig-web nobody reader must read them (9.1). Restrict the repository directory yourself if the host is shared. The .debug file is 0600 (it can contain secrets even though passwords are masked). Parallel-fetch worker scratch files are owner-only (they live in a private temp dir).

Mail

  • SMTP header-injection -- from, subject, and every recipient have CR/LF stripped before the headers are written.
  • No plaintext fallback -- tls=starttls|ssl never silently downgrades to an unencrypted send; if TLS fails the mail is skipped and logged.

Deliberate NON-mitigations (do not "fix" these blindly)

  • Repository is umask-readable by design (9.6) -- not a permissions bug.

Notification subsystem (Mailer / Report)

  • send_summaries builds @global_rows from @results and sends the global summary to the email: to= recipient, then groups devices by their to= override and sends each distinct override recipient one mail with only its own devices (dedup). The global recipient is never double-mailed.
  • The mail is multipart: a multipart/related wrapping a multipart/alternative (a plain-text summary built by build_report_text -- the stats and device tables in text, no diffs -- and an HTML part built by build_report_html), plus the inline logo image. Conventions and gotchas

  • Phases are sacred. Never fetch in phase 1 (parse/register); never rely on parse-time side effects in phase 2.
  • Models never abort the run. Return failure from do_fetch; let the pipeline record it and continue. Only table/allowlist errors abort, and only before fetching.
  • Package my lexicals limit external testability. Several Mailer structures (%email_config, $rep_url, @results) are file-scoped lexicals; a test can only reach them through the module's own entry points (hence the small _test_set_rep hook used by the mail tests). If you add a structure that a test must drive, expose it through an entry point rather than expecting external assignment to work.
  • -P isolates package state. A value a worker must return to the parent goes through record_result (the result sink), not a package variable (Parallel fetch (-P N)).
  • MIME is byte-sensitive. The summary mail's MIME must match the fetchconfig-web mailer exactly (CRLF, folded boundaries, 12-byte random boundaries, base64 wrapped at 76). Do not "tidy" the send_mail emission.
  • Secrets. Any new code that sends a credential uses print_secret; any new code that logs a device-table line uses mask_secrets; any new code that renders config content in a report uses mask_line.
  • Timeouts and keep are validated. A non-positive-integer timeout/fetch_timeout/banner_timeout/prompt_settle_ms falls back to the default (via dev_option_posint/the dev_option numeric guard); a non-positive-integer keep is rejected at load time (it would otherwise delete every backup).
  • Version/CHANGES discipline. Bump Constants.pm, add a CHANGES entry (<=80-char lines, LF-only), and keep README + the HTML manual in step with the code -- the HTML is generated from its .md via tools/md2html.py (run by make doc, which launches the Python tools through tools/pyrun: python3 on Linux, python on AIX).
14

Backup-history DB writer (optional)

Off unless a db: line is set (default: level). It records two timelines to PostgreSQL for a dashboard; the engine only writes, never issues DDL. Module: fetchconfig/History.pm. DBI/DBD::Pg load only when db: is set. The .status file is unchanged.

Two timelines (different cardinality):

  • Run / health history: one row per device per run, success or not. Dense. Table backup_runs.
  • Change history: one row per SAVED backup (with a sha1). Sparse. Table backup_versions. A per-device current snapshot is kept denormalized in backup_current.

Data path (parent only; never in -P workers):

  1. During the fetch, nothing touches the DB. Detector::fetch_device records the run through Mailer::record_result, now also carrying size_bytes, path, file_timestamp and sha1 for a RETAINED backup (the metadata Abstract::dump_config stashes on the model instance as {saved}). Expiry emits Mailer::record_expire events. Under -P these ride the result sink and are replayed into the parent.
  2. At end of run (fetchconfig.pl, after run_fetch_phase, before send_summaries), History::finish builds the ops from the replayed results and writes a per-repository WRITE-AHEAD spool file (<repo>/.db-<pid>-<ts>, a dotfile, temp+rename).
  3. It then drains every spool file into the DB, oldest first, one transaction per file. Two runs may share a repository with no lock, so each file is first claimed by an atomic rename to <repo>/.db-<pid>-<ts>.draining.<drainer-pid> before it is read -- rename(2) lets exactly one drainer win a given file, so a file is never applied twice concurrently (which also removes the inventory-component duplication hazard). A file is unlinked only after COMMIT; on the first read/apply/commit failure the drainer rolls back, renames the file back to its claimable name, and stops (that file and later ones wait for the next run). Because files are taken oldest-first, losing a claim means another drainer already holds the oldest-unhandled file, so this drainer stops rather than apply a newer file ahead of it -- preserving order across drainers without a lock. Before each repo is scanned, _reclaim_orphans recovers any .draining.* file whose owner PID is dead (kill 0: ESRCH) by renaming it back to its claimable name, and drops any spool -- claimed or not -- older than db_max_outbox_days.
  4. History::finish logs its own -----[DB writer]----- section (same 92-char width as the mail's -----[email]-----): the divider first, then any spool or drain warnings, then the result line History::status_line ("all N record(s) written; outbox empty", or the INCOMPLETE form). This runs before send_summaries and independent of "email:", so a no-mail run still reports the DB outcome. When "email:" is set, the main summary mail also renders a status box inside the card from History::mail_status (green = written, red = incomplete, grey = no db:); _db_status_box_html builds it and the per-device override mails omit it. Log and mail read the one %summary that finish set. db_sslmode defaults to disable (a local DB on the same box); set require or stronger for a DB across a WAN. Mail markup is Outlook-safe: the report button is a VML <v:roundrect> and the status pill a one-cell <td> badge, each behind [if mso] with the plain <a>/<span> behind [if !mso] (VML namespaces + an OfficeDocumentSettings DPI block are in build_report_html's <head>); the box title and pill are separate <td>s; and the summary tables use soft zebra shading (@ROW_BG) to separate rows instead of grid lines. Each cell sets its colour via both the bgcolor attribute and CSS (OWA's sanitizer can drop a cell's CSS background). The table uses border-collapse: collapse with no cell borders: that removes the sub-pixel inter-row gap Word would otherwise paint with the table background (the faint 1px seam it drew under the darker band), so each row's own shade is all that shows - no single table or border colour has to stand in for both shades. send_mail sends the HTML part as quoted-printable (not 8bit): the markup has long lines (a table row is one line), and an MTA that folds a raw line past the 998-octet SMTP limit corrupts the HTML mid-tag; QP soft-wraps at 76 chars.

Write-ahead means the records hit disk before the DB is touched, so a DB outage only defers the drain (the run always completes) and nothing is lost. The claim rename, the rename-back on failure, and the dead-PID orphan reclaim make the drain crash-safe too: a drainer that dies mid-write leaves its DB transaction uncommitted (the backend rolls it back when the connection drops) and the spool file intact under its .draining name, to be reclaimed and retried on a later run. Every op is idempotent (INSERT ... WHERE NOT EXISTS, keyed UPDATE/upsert), so the commit-then-crash re-apply window is a no-op. The PID-liveness reclaim assumes one host per repository -- the same assumption the .db-<pid>-<ts> naming already makes; the db_max_outbox_days drop is the final backstop that clears any orphan a PID check cannot (e.g. a reused PID, or a host that cannot signal-probe).

--db-backfill (History::backfill) reconstructs the history from the backups already on disk, for first enabling db: on an existing install. It writes directly (not via the spool - this is a manual maintenance pass, not the fetch path): it connects once (aborts if unreachable), and per device enumerates the on-disk backups the same way -l does (device_info -> dev_option("repository") -> scan_dir -> sort_backups_desc). For each backup it inserts a backup_versions row - sha1 recomputed by _sha1_file, which hashes the file's raw bytes and so is identical to the live save's add("$_\n") because the file IS those bytes - and a backup_runs row (run_end = the file's file_timestamp from backup_epoch_from_filename, state success, changed, duration NULL), both via _apply_op; then one backup_current row (_current_row, from <dev_id>.status plus the newest backup) for a device that has none. Every write is guarded by a prior existence SELECT (_row_exists), so a re-run skips present rows and does not re-hash, and a backup_current a live run wrote is never overwritten; work is committed per device (rolled back on a DB error, which is counted and the run continues). -T runs the same existence checks and counts but does no hashing and no writes. The dense run history cannot be rebuilt (unchanged/failed runs leave no file), so only the saved change-events are added. It logs its own -----[DB backfill]----- section (same width as -----[DB writer]-----): a process: <path> debug line per backup, then the counts summary and a final Success (or, on a failure, the error count).

Device-id rename on the outbox. --rename-device-id (Locking covers the table lock) emits one op=rename record (old_dev_id/new_dev_id) into the device's repository spool via History::queue_rename, then drains it (History::replay) at the end of the command. _apply_op's rename kind runs UPDATE {backup_current,backup_runs,backup_versions} SET dev_id=new WHERE dev_id=old in the file's transaction; it is idempotent (once applied, WHERE dev_id=old matches nothing) and needs GRANT UPDATE (dev_id) on the three tables (fetchconfig-web side). If the DB is down the op simply stays in the outbox, like any other, and the next run's drain -- or an explicit --replay-db-change (History::replay over every loaded device's repository, no fetch) -- applies it. A live pre-check (row_count_for_dev) refuses a rename into an id that already has rows; if the DB is unreachable at rename time the apply-time transaction is the backstop. When the inventory tables are present the rename also updates device_inventory, device_inventory_component and device_inventory_history (six UPDATEs rather than three).

SNMP device inventory (9.80, three tables owned by fetchconfig-web: device_inventory, device_inventory_component, device_inventory_history). These ride the same outbox as the backup history. Mailer::record_inventory / record_inventory_component (parent, or replayed from the -P sink) collect the per-device result; History::finish turns it into ops and _apply_op handles the new kinds: op=inv_current upserts the device_inventory row (capturing the prior hw_set/os_version first), op=inv_reset clears the device's components (a snapshot replace), and op=inv_component inserts each component (is_primary as 't'/'f'), including its firmware/ROMMON rev in fw_version (web schema 2.16); op=inv_current likewise carries the device's own sysname/syslocation/syscontact (web schema 2.17). _probe_inv_tables checks, once, whether each added column exists (via pg_attribute/pg_class, which can't poison a transaction): the component INSERT omits fw_version when device_inventory_component.fw_version is absent, and the inv_current upsert omits the three sys columns when device_inventory.sysname is absent, so the engine runs against a 2.15, 2.16 or 2.17 DB without a 42703 (the sys fields are current-state only -- never part of change detection). The current-row logic is tri-state: a disabled status is UPDATE-only (never inserts), a failed attempt keeps the existing data (only the status/timestamps move), and a successful attempt upserts everything, conditionally advances changed_at, and -- derived during the drain, not stored on the result -- inserts a device_inventory_history row (INSERT ... WHERE NOT EXISTS, note = initial/members/os/both) only when hw_set or os_version actually changed. Every inventory op is gated behind a one-time pre-check (_probe_inv_tables, a pg_class lookup -- no to_regclass, which is 9.4+): when the tables are absent _apply_op returns success without touching them, so an engine pointed at a web side not yet upgraded is a no-op. All DML is 8.2-safe and uses DBI placeholders, exactly like the backup-history ops.

Per-version line deltas (lines_added/lines_removed, web 2.12). These are the +added/-removed of Abstract::line_delta (a dependency-free diff: trim the common prefix/suffix, then an LCS-length DP; added = curr - LCS, removed = prev - LCS) over $mod->config_norm_lines, which returns the file as the ignore/canon-normalized line list - the SAME view config_equal compares, via the new config_ignore_re / config_canon model hooks (CiscoASA's constant regex, GenericTemplate's cur_ignore_re/cur_canon, base = raw). The live writer computes the delta in Detector::fetch_device (previous stored config vs the just-saved one) and carries it on the result into the version op; the oldest/first version is the baseline (NULL). backfill walks a device oldest->newest keeping the previous normalized lines, and either inserts a new row with the delta or UPDATEs an existing row whose lines_added is still NULL. The columns are owned by fetchconfig-web; _connect probes information_schema once ($delta_cols) and the writes include the two columns only when present, so the engine stays compatible with a web side not yet upgraded. Parity note: a GenericTemplate device has no template loaded under backfill, so its cur_ignore_re is undef and its backfilled delta is over raw lines - accepted; live runs (template loaded) count the normalized view.

Pre-9.5 PostgreSQL (production is 8.2.23): no ON CONFLICT/MERGE/jsonb. Append-only inserts use INSERT ... SELECT ... WHERE NOT EXISTS (<key>); backup_current is UPDATE-else-INSERT (a successful run advances last_good_at/last_good_size, a failed run leaves them untouched; two UPDATE shapes avoid a boolean bind in a CASE). All DML uses DBI placeholders. The writer role needs SELECT as well as INSERT/UPDATE on the three tables, because the idempotency subqueries and the UPDATE WHERE/value expressions read them; that grant is created by fetchconfig-web (fetchconfig-web-dbsetup.pl --upgrade), not by the engine.

All DB timestamps (run_end, last_good_at, expired_at, file_timestamp) use one convention: the box's LOCAL wall-clock encoded as seconds (via timegm of the local parts), not a true UTC instant. fetchconfig and its fetchconfig-web run on a single box in a single timezone, so the stored values are directly the local time and fetchconfig-web renders them as-is, with no timezone conversion. file_timestamp is derived from the same parts at save and at expiry (Abstract::backup_epoch_from_parts), so the keyed row matches; the filename tz token is ignored, and timegm does not consult the host zone. (Spool file-age pruning uses real elapsed time, independent of this display convention.)
